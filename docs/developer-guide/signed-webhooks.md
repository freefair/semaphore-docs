# Signed Webhooks

Enhanced Edition uses one protocol for outbound audit delivery and inbound workflow webhooks. The protocol authenticates the exact HTTP method, raw request target, event identity, signing time, key identity, and payload bytes.

[[toc]]

## Protocol

The protocol version is `semaphore.webhook.v1`. Every signed request carries each of these headers exactly once:

| Header | Value |
|---|---|
| `X-Semaphore-Webhook-Version` | `semaphore.webhook.v1` |
| `X-Semaphore-Event-ID` | Stable logical event ID, 16–128 allowed ASCII characters |
| `X-Semaphore-Timestamp` | Canonical Unix time in whole seconds |
| `X-Semaphore-Key-ID` | Non-secret identifier beginning with `swhkid_` |
| `X-Semaphore-Signature` | `v1=` followed by exactly 64 lowercase hexadecimal characters |

The payload is limited to 256 KiB. The request target is the raw path plus raw query string, including its original escaping, ordering, and duplicate query parameters. A receiver must not parse and reconstruct it before verification.

## Canonical Bytes

The signature input is a binary, length-framed sequence:

```text
u16be(len(version)) || utf8(version) ||
u16be(len(method)) || ascii(method) ||
u32be(len(request_target)) || utf8(request_target) ||
u16be(len(event_id)) || ascii(event_id) ||
i64be(timestamp_seconds) ||
u16be(len(key_id)) || ascii(key_id) ||
u64be(len(payload)) || payload
```

Lengths are byte counts, not character counts. The MAC is `HMAC-SHA-256(decoded_secret, canonical_bytes)`. Remove the `swhsec_` prefix and decode the remaining unpadded Base64url value to obtain the 32-byte HMAC key. Compare the supplied and calculated MACs in constant time.

The stable interoperability vector is:

| Field | Value |
|---|---|
| Secret | `swhsec_AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA` |
| Method | `POST` |
| Request target | `/hooks/run?x=%2F` |
| Event ID | `evt_0123456789abcd` |
| Timestamp | `1700000000` |
| Key ID | `swhkid_test_0001` |
| Payload | `{"ok":true}` encoded as UTF-8 without a trailing newline |
| Signature | `v1=0f826cf54ef1745b79f87360111254f17b4589ccb27f2ad88b1d7a1f88ed52f2` |

## Receiver Verification

Perform these checks before parsing the JSON body or causing a side effect:

1. Read the raw body with a 256 KiB limit and preserve the raw request target.
2. Require each protocol header exactly once and validate its strict syntax.
3. Resolve the key ID against the receiver's current and overlap keys without revealing which candidate matched.
4. Rebuild the canonical bytes and compare the HMAC in constant time.
5. Require the timestamp to be within five minutes of the receiver's UTC clock. Both exact five-minute boundaries are accepted.
6. Atomically claim `(receiver, event_id)` in durable storage before processing the body. Return the previously recorded result or reject the duplicate without repeating the side effect.
7. Only after the claim succeeds, decode the body and execute the operation.

The event ID remains stable across outbound retries, but Semaphore creates a fresh timestamp and signature for every attempt. Deduplication must therefore use the event ID, not the signature, timestamp, attempt number, or key generation. Keep replay identities for at least as long as the sender can retry or an operator can replay retained events.

## Key Rotation

Signing secrets are generated by the server, encrypted at rest, and returned once. Status and history APIs expose only key IDs and generations.

Use the same two-phase procedure for audit export and workflow webhook receivers:

1. Create the initial current key and store the displayed secret in the receiver's secret store.
2. Stage a next key and add it to the receiver without removing the current key.
3. For audit export, send a controlled delivery with `key=next`. For inbound workflow webhooks, send one signed request with each key.
4. Promote the staged key. Semaphore uses it as the only production signing key; the old current key remains accepted as the retired overlap key.
5. Revoke the retired key after senders and receivers have converged.

Only a staged key whose generation is newer than current can be promoted. A retired predecessor cannot be promoted back. Every mutation uses the latest signing or trigger revision and returns `409 Conflict` for stale or invalid state.

## Outbound Audit Delivery

Audit deliveries are always HTTP `POST` requests to the configured HTTPS endpoint. The exact configured path and query are signed. The immutable `semaphore.audit.v1` payload and event ID stay unchanged across retries; `X-Semaphore-Timestamp` and `X-Semaphore-Signature` are regenerated for each attempt.

The optional legacy Bearer credential remains independent and may be sent alongside the signing headers during migration. It is not an HMAC secret and cannot select a signing key.

Attempt history contains only the attempt number, event ID, key ID, signing time, bounded outcome and reason, optional HTTP status, and completion time. Payloads, secrets, signatures, request headers, response headers, bodies, and raw network errors are never returned or retained in that history.

## Inbound Workflow Webhooks

The public route is:

```text
POST /api/workflow-triggers/{project_id}/{workflow_id}/{trigger_id}/webhook
```

It accepts only the signed protocol. Supplying an `Authorization: Bearer` credential does not fall back to API-trigger authentication. API triggers retain their separate `/api` route and opaque `swt_` credential contract.

Semaphore verifies the raw request before strict JSON mapping and atomically stores a replay identity derived from the trigger ID and event ID before starting a workflow. The first valid event returns `201 Created`; every repeat of the same event ID returns `409 Conflict`, including concurrent repeats and a repeat after key rotation. Authentication, freshness, key-state, and signature failures intentionally collapse to `401 Unauthorized`. Oversized bodies return `413 Payload Too Large`.

Authenticated trigger history exposes the safe event ID, key ID, signed time, and replay count. It does not expose the event hash, payload, signature, secret, headers, input snapshot, or internal verification reason.

## Administration APIs

Audit signing lifecycle:

| Method and path | Result |
|---|---|
| `POST /api/audit-webhook/signing-secret?revision={revision}` | Create and reveal the initial secret once |
| `POST /api/audit-webhook/signing-secret/stage?revision={revision}` | Stage and reveal the next secret once |
| `POST /api/audit-webhook/test?key=current` | Persist and send a controlled current-key attempt |
| `POST /api/audit-webhook/test?key=next` | Persist and send a controlled next-key attempt |
| `POST /api/audit-webhook/signing-secret/promote?revision={revision}` | Promote the staged key and retain the old key for overlap |
| `DELETE /api/audit-webhook/signing-secret/next?revision={revision}` | Revoke the staged or retired next key |
| `GET /api/audit-webhook/deliveries/{delivery_id}/attempts` | Read bounded, redacted attempt history |

Workflow webhook lifecycle uses a JSON body containing the current trigger `revision`:

| Method and path suffix | Result |
|---|---|
| `POST .../{trigger_id}/webhook-signing/bootstrap` | Create a current key for a migrated unsigned webhook trigger |
| `POST .../{trigger_id}/webhook-signing/stage` | Stage and reveal the next secret once |
| `POST .../{trigger_id}/webhook-signing/promote` | Promote the staged key |
| `POST .../{trigger_id}/webhook-signing/revoke` | Revoke the staged or retired next key |

All lifecycle reads and mutations use existing audit-webhook administrator or workflow-administrator authorization. Creating a new webhook trigger creates its initial signing key in the same operation and returns the one-time `webhook_signing_secret` field.

## Operational Failure Policy

- A configured audit endpoint without a current signing key remains queued and is not sent unsigned.
- Missing encryption, invalid signing state, or failed decryption fails closed.
- A migrated workflow webhook without signing state rejects invocation until an administrator bootstraps a key.
- A signature or secret never appears in read APIs, logs, audit details, browser persistence, backups, or delivery history.
- The UI holds a revealed secret only in transient component state and clears it on dismissal, dialog reopen, page reload, or navigation.
